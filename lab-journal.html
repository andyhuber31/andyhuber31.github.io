Spanning Tree and LACP: Building a Redundant Switching Lab

I started by recording the existing links, EtherChannels, and spanning-tree roles on Paul, Ringo, and George. My next stage is to extend VLAN 310 across the switches and then add a direct Paul–George link so I can compare spanning tree before and after a redundant path exists.

Goal

Use command output to explain root-bridge selection and port roles, and observe how spanning tree handles a redundant switch path alongside LACP EtherChannels.

Current stage: The initial switching baseline is captured. VLAN 310 checks and the direct Paul–George link are still part of the work in progress.

The baseline has two switch-to-switch connections. Each is an eight-member LACP EtherChannel. The direct Paul–George link is planned for the next stage.

My prediction

I expect spanning tree to treat each LACP EtherChannel as one logical port, even though the channel contains eight physical interfaces.

The baseline supports this: Paul’s EtherChannel output lists eight bundled members in Po2, while its spanning-tree output lists Po2 as a single root port.

What this tells me

  • Use the bridge IDs to explain root selection. The switch with the lowest bridge ID wins for a VLAN; priority is compared before the MAC address. Configuration order is not the election rule.
  • Keep physical members and logical paths separate. Eight bundled interfaces appear as one port-channel in spanning tree. The member count alone does not prove a redundant switch path exists.
  • Distinguish bundling from traffic distribution. The output confirms eight active members, not equal use of all eight. EtherChannel uses a hash to select a member; I have not measured traffic distribution in this exercise.

What I’m checking next
